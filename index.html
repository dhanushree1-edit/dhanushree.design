The brief
One system for every screen

        

          
The goal was a structured set of visual guidelines, reusable components and design principles, so every CureMeAbroad screen follows the same language, and design gets faster and easier to scale.

          
The system is built for a 1:1 handoff: every variable carries the real CSS name developers see in Dev Mode, and text style names are literal Tailwind classes.

          
  • UI/UX design
  • Colours, type, spacing, icons
  • Component design
  • Responsive layouts
  • Documentation
  • Working with developers

        

      

    


    

      
01 · Brand

      
Credible, with warmth

      
A plus-mark for care, set beside a calm wordmark. The logo comes in default, on-dark and mono versions, with a clear-space rule of half the icon height.

      
      

      

      
Do and don’t. The coloured icon only sits on neutral surfaces. On brand violet, use the mono white version.

Ground rules

          
    
            
  • Tokens first. Pick from base/* or a text style. Raw hex never leaves Primitives.
    • 
            
  • Match the code. Variant and property names follow shadcn/ui, so handoff is one to one.
    • 
            
  • Violet identity. Primary actions and active states are violet-500; overlays and containers stay neutral.
    • 
            
  • Focus states. A violet border plus a ring-30 halo on violet controls; a grey outline only on neutral surfaces.
    • 
            
  • One light theme. A single Light mode, no dark mode anywhere in the file.

05 · How it works

      
A guide the team can follow

      
I wrote a step-by-step guide inside the file, so anyone at CureMeAbroad can use and extend the system without breaking it.

      
  1. 02
    Publish the library
    The file is published as a team library, so every CureMeAbroad file pulls the same components, styles and variables.
  2. 03
    Five collections, one source
    Primitives Core, Primitives Type & FX, Semantic, Custom responsive scales and the Icon Library. Designs only ever use Semantic.
  3. 04
    Change the primary colour
    Point base/primary at another step of the violet ramp, and every button, link and focus ring updates at once.
  4. 05
    Neutral ramp
    Greys from neutral/0 to neutral/1000 live in Primitives Core and feed every surface, border and muted text.
  5. 06
    Alpha variables
    Hover states use alpha tokens, so primary at 90% is a variable, not a hand-picked colour.
  6. 07
    Save a text style
    New type is saved as a named style, so headings stay consistent across pages.
  7. 08
    Light mode only
    The Semantic collection ships a single Light mode. There is no dark mode anywhere in the file.
  8. 09
    Room for new themes
    A new mode can be added to Semantic later for a sub-brand, without touching any component.
  9. 10
    Edit the main component
    Changing the main Badge updates every instance across the file.
  10. 11
    Spacing and radius tokens
    Padding and corners come from spacing-1, spacing-2 and rounded-full, never typed-in numbers.
  11. 12
    Add a variant
    A Warning button is added with base/warning and base/warning-foreground, in line with the rest.

      

        
For developers
The stack is Next.js, TypeScript, Tailwind CSS v4 and shadcn/ui. Every base/* token maps to a shadcn CSS variable, so components installed in code are pre-wired to the same values as Figma.

The brand

        
No complexity, no friction

        
PlugnPlay is a modern electronics brand for everyday digital accessories: mice, keyboards, headsets, earbuds and other peripherals, for work, gaming and entertainment.

        
Its products are easy to use and instantly compatible. The whole identity grows from that promise: plug it in and start using it.

      


      

        
Logo

        
A plug, a play button, one cable

        
The wordmark joins a plug icon, for connection and compatibility, with a play icon, for instant use. A cable line runs beneath it for continuous connectivity, and custom geometric letters keep it modern and simple.

        
The PP submark folds the plug and play symbols into an infinity-style shape, for endless connectivity. It works where the full logo is too wide, such as app icons, tags and packaging tape.

Concept project · Accessibility · 2026

        
PhonePe Scan & Pay,
for every kind of user

        
An accessibility audit of PhonePe’s Scan & Pay flow, and a redesign of the screens that fail blind, low-vision, colour-blind and deaf users.

        See the redesign →
        View the Figma file ↗
      

    

    

      
18 findings
Checked against WCAG 2.2, ranked by severity

      
6 critical
Each one can block a payment for a blind user

      
22 screens
Redesigned in PhonePe’s own visual language

    

    
An independent concept project, not affiliated with or endorsed by PhonePe. Role: UI/UX designer · Platform: Android with TalkBack · Tools: Figma, Claude.

  


  

    

      
Now let’s take a look at

      
Problem & Solution

      

        

        
        
        
Problem
Paying with a QR code looks simple. With TalkBack it means an unlabelled Scan button, a camera you can’t aim, a payee name that may not be read out, a UPI PIN typed blind, and a result you can’t hear. With money involved, a missed announcement is not a small thing.

        
Solution
Say the important thing in words at every step: label every control, guide the camera with sound and vibration, read the payee and amount together, never speak PIN digits, and announce every result with its own icon, wording and vibration.

        
      

    

  


  

    

      
Where Scan & Pay breaks

      
Eight barriers I found by walking the flow with TalkBack on. Each maps to a finding code.

      

        
        
  1. 01
    Unlabelled Scan
    Scan and other icon buttons may have no label, so TalkBack only says “button”.
    F2
  2. 02
    No aiming help
    Nothing guides a blind user to point the camera at the QR code.
    F5
  3. 03
    Silent payee
    The payee name and verified badge are not announced together.
    F7
  4. 04
    Amount unread
    The amount is read as separate digits, or not read back before paying.
    F8
  5. 05
    Risky PIN screen
    The UPI PIN screen may not work with TalkBack, and digits can be overheard.
    F12
  6. 06
    Result unheard
    Success is animation and sound. Amount, payee and status go unannounced.
    F15
  7. 07
    Sound-only alerts
    Payment alerts rely on sound, with no vibration or flash for deaf users.
    F16
  8. 08
    Colour-only states
    Failed and pending are told apart mostly by red and orange.
    F14

  2. Process

My role

        
What I owned, and what I didn’t

        

          
What I worked on
Audit and findings
Mapped the Scan & Pay flow and reviewed each step against WCAG 2.2: 18 findings, ranked by severity, each with a fix and a place on the roadmap.
Interface design
Redesigned the screens at the highest risk (Home, scan, review, PIN, results, timeout and alerts) in PhonePe’s own visual language.
A new feature
Designed Quick Access, a panel opened with a physical trigger and filled with the tasks a person repeats every day.

          
Outside my scope
User testing
The findings are expected problems from an expert review. They have not yet been confirmed with blind or deaf participants.
Development
This is a design proposal. Spoken results, haptics and a physical trigger need real code on a real phone.
Final sign-off
The UPI PIN screen belongs to NPCI. A secure, accessible version has to be designed with them.

        

      


      

        
Process

        
From audit to redesign

        
I moved from structure to interface in clear steps, so each decision built on the one before it.

        
  1. 1Map the flowA 10-step Scan & Pay chart and the app’s structure
  2. 2Audit18 findings checked against WCAG 2.2
  3. 3SimulateSeven colour-blindness simulations
  4. 4RoadmapThree phases, cheapest fixes first
  5. 5Redesign17 screens plus every result state
  6. 6Quick AccessA new panel with a Settings switch

      


      

        
Research

        
Learning PhonePe’s visual language first

        
Before auditing anything, I studied how PhonePe looks and speaks, so the redesign would still feel like PhonePe.

        

          
Typeface
PhonePe uses its own custom humanist sans-serif, made with Mumbai’s November Design in 2019 and used everywhere from the app to billboards. It isn’t publicly available, so I worked with Inter as the closest open match. The PhonePe logo itself is custom lettering, not a font.

          
Icons
Simple, rounded icons, mostly purple on a light background, sitting in grids by section with a short label underneath. I checked whether every icon has both a visible label and a screen-reader label, and whether the light purple backgrounds have enough contrast.

          
Scan button
A prominent purple QR icon, larger and in the bottom navigation in the newer design, where it’s easy to reach with a thumb. It’s easy to see, but a blind user needs it read as “Scan QR code to pay”, early in the focus order (F2, F4).

          
Illustrations
PhonePe’s flat, colourful illustrations of everyday Indian life are decorative, so a screen reader should skip them, or read one short description when they carry meaning.

          
The Beam
PhonePe’s purple capsule shape, used across ads and banners. I reused it for buttons and severity tags so the new screens feel on-brand.

        

        

          
          
        

      


      

        
Information architecture

        
How the app is organised

        
PhonePe has six top-level areas, and Home holds six service sections. Scan and Pay sits one level down, which matters for anyone who has to swipe to reach it.

        
      


      

        
User flows

        
One flow, ten steps, before and after

Learnings

        
What I’d carry forward

        

          
What I learned
  • When I measured my own redesign, three switches were 34 px tall and my notes about tiny text were wrong. Numbers beat trusting my eye.
  • Most fixes were the same move: put the important state in text, not only in colour, an icon or a sound.
  • Quick Access started as an accessibility feature and turned out useful for anyone in a hurry.

          
What comes next
  • Test the flow with blind and deaf participants
  • Mark each finding confirmed, partly found or not found
  • Design the PIN screen together with NPCI
  • Build a coded prototype with spoken results and haptics
  • Test text at 200% and landscape on a real phone
